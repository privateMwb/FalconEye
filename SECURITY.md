# Security Policy

## Supported versions

FalconEye is a small, individually maintained project. Security fixes are made on the
`main` branch and shipped in the next release; older releases are not patched.

| Version | Supported |
|---|:-:|
| `main` and the latest release | ✅ |
| Anything older | ❌ |

## Reporting a vulnerability

**Please do not report a suspected vulnerability in a public issue, pull request, or
discussion.** Use GitHub's private reporting instead, so a fix can be prepared before the
details are public:

1. Open this repository's **Security** tab.
2. Choose **Report a vulnerability**.
3. Describe the problem.

A useful report includes:

- what is affected (the `Metrics` middleware, the example server, the dashboard, the demo
  image) and the commit or release you tested;
- steps to reproduce, ideally the exact `curl` request or input bytes;
- what you expected and what happened (a crash, a sanitizer report, wrong data);
- any suggested fix.

This is a spare-time project, so responses are best-effort. You will get an
acknowledgement and an honest assessment, and credit in the fix if you want it.

## Security model: read this before deploying

FalconEye is built for development and demonstration. It is designed to run on a trusted
machine or network, and **it has no authentication, authorization, or encryption**. This is
a deliberate scope limit, not an oversight:

- **`/api/metrics` is unauthenticated.** Anyone who can reach the port can read recent
  requests: route patterns, methods, status codes, timings and timestamps. Route
  *patterns* (`/api/todos/:id`) are recorded, not raw paths, query strings or bodies.
- **No TLS.** Traffic is plaintext HTTP.
- **CORS is a browser rule, not access control.** The example server only allows
  `http://localhost:5173`; that does not stop `curl` or another server from reading the
  endpoint.
- **The example server is not hardened.** `backend/src/main.cpp` and the example routes
  exist to demonstrate the middleware. Replace them with your own application.
- **The metrics are in memory and unbounded in time, not in size.** Only the latest
  entries are kept (50 by default), and nothing is written to disk.

If you use `Metrics` in a real service, keep `/api/metrics` behind a firewall or private
network, or put an authenticating, TLS-terminating proxy in front of it.

## Hosted demo

The hosted-demo setup (`Dockerfile.demo`, `render.yaml`) is public by design and protected
differently:

- The container runs as an unprivileged user and keeps everything in memory.
- Its front door forwards only `GET /api/metrics` and `GET /api/health`; every other path
  and method is answered with `404`.
- CORS is answered only for the exact origins in `ALLOWED_ORIGINS`.
- The traffic it records is generated by the container itself, not by visitors.

What it does not do: authenticate visitors or rate limit them. Anyone can read the
(synthetic) metrics and make the free instance wake up.

## Automated checks

CodeQL, clang-tidy, sanitizer runs (ASan, UBSan, TSan) and ClusterFuzzLite fuzzing run in
CI. They reduce risk; they do not prove the absence of bugs.
